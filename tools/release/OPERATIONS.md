# Release, monitoring and recovery controls

Production is GitHub main only. Required checks: validate/test, security and SonarQube. SonarQube runs on the trusted local machine because that is the owner's installed server; public GitHub-hosted runners cannot reach localhost. Do not expose the server, copy its admin token into public workflows or register an unrestricted self-hosted runner for a public repository.

After committing a complete release, run tests with coverage and `node tools/release/sonar-gate.mjs`. Keep the analysis token only in the protected file described by the script or SONAR_TOKEN. The script submits a pending commit status, runs the real scanner and waits for the real quality gate, then posts success/failure for that exact SHA. A failed or missing result must block promotion; a configured properties file is not a passing scan. Mobile repositories have their own properties and the same script is copied into their tools directory.

Release workflow rechecks source, dependencies and schema; it does not blindly apply unreviewed SQL. Rehearse migrations in staging, capture Time Travel state, apply additive changes deliberately and verify metadata before app promotion. Keep the `bcrypt-v1:` verifier in any rollback candidate. API /health exposes the promoted SHA; /api/platform/readiness requires a platform operator and checks schema and R2. Worker logs and sampled traces are explicitly enabled. Never add passwords, request bodies, student names or contact details to logs.

Operational response targets (targets, not measured guarantees): failed release immediately investigated; error rate >1% over 5 minutes, dead-letter increase or oldest pending event >15 minutes triggers investigation; monitor D1 CPU/row usage and paid-plan budget daily. External alerts require a real configured destination and are not certified by these files. Dispatchers emit sanitized statistics; uncertain email outcomes require operator reconciliation before resending.

Database recovery workflow runs daily and on demand: export to a private temporary SQL file, encrypt with an independent 32-byte key, decrypt, restore to memory and verify integrity/foreign keys. It uploads only encrypted content plus a checksum manifest and erases plaintext. Retention is 30 days. BACKUP_ENCRYPTION_KEY is a repository secret; escrow it outside GitHub separately. This provides a daily export target RPO of 24 hours plus automatic D1 Time Travel; actual recovery RTO must be measured by the real drill. D1 Time Travel affects the shared database, so never restore live production as a tenant-level test.

R2 objects are separate from D1 snapshots. The object recovery drill copies an authorized genuine source object into the isolated staging bucket and verifies bytes/checksum. It does not overwrite production or certify independent off-provider retention of the whole bucket. Retain private source keys/checksums in protected evidence only. A storage-wide export requires approved retention/budget and encryption, not a public backup bucket.
